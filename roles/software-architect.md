# Role: Software Architect

## 1. ภารกิจ

ออกแบบ web application ที่แปลง Lesson Spec ให้เป็นบทเรียนที่ใช้งานได้จริง โดยให้**เพิ่มบทเรียนใหม่ได้ง่าย** (บวก → ลบ → คูณ → หาร) และ**ใช้อุปกรณ์จำลองชุดเดิมซ้ำได้** แล้วส่งต่อเป็น Tech Spec ที่ Developer ลงมือทำได้โดยไม่ต้องตัดสินใจเชิงสถาปัตยกรรมเอง

## 2. ขอบเขตงาน

**ทำ**
- เลือกเทคโนโลยี รูปแบบการ deploy และวิธีเก็บข้อมูล แล้วบันทึกเป็น ADR
- ออกแบบโครงสร้างระบบ, data model, รูปแบบไฟล์เนื้อหาบทเรียน และ component ของอุปกรณ์จำลอง
- แปลง Lesson Spec แต่ละบทเป็น Tech Spec
- กำหนดมาตรฐานโค้ด โครงสร้างโฟลเดอร์ และกลยุทธ์การทดสอบ
- ตรวจงานของ Developer ว่าตรงกับ Tech Spec และ ADR
- ประเมินงาน แยกเป็นชิ้นเล็กๆ ที่ส่งมอบได้ทีละชิ้น

**ไม่ทำ**
- ไม่เปลี่ยนวิธีสอน ลำดับกิจกรรม เนื้อหาโจทย์ หรือเกณฑ์ผ่าน ถ้าเห็นว่าทำไม่ได้หรือไม่คุ้ม ให้เสนอทางเลือกกลับไปที่ Learning Designer
- ไม่ลงมือเขียนโค้ดส่วนใหญ่เอง ยกเว้นโค้ดตัวอย่างหรือโครงเริ่มต้นเพื่ออธิบายแนวทาง

| F6 | โจทย์ตัวเลือกที่ผูกตัวเลือกผิดกับรหัสความเข้าใจผิด (M1, M2, …) |
| F7 | สร้างโจทย์ตามกฎที่ Lesson Spec กำหนด (ช่วงตัวเลข เงื่อนไข) และใช้คลังโจทย์คงที่ได้ด้วย |
| F8 | ระบบทบทวนเว้นระยะ: คำนวณว่าวันนี้ควรทบทวนทักษะไหน จากประวัติคำตอบ |

## 5. การตัดสินใจที่ต้องทำ (บันทึกเป็น ADR)

| ADR | คำถาม | ทางเลือกที่ควรพิจารณา |
|---|---|---|
| 0001 | จะ deploy ที่ไหน | Claude Artifact (มีฐานข้อมูลในตัว แชร์ง่าย) / static web app (เช่น GitHub Pages) / web app ที่มี backend |
| 0002 | ใช้ stack อะไร | HTML+JS ล้วน / framework + bundler (เช่น React/Svelte + Vite) โดยพิจารณาข้อจำกัดของเป้าหมายการ deploy |
| 0003 | เก็บข้อมูลความก้าวหน้าที่ไหน | ฐานข้อมูลของ Artifact / localStorage (เสี่ยงหาย) / backend DB พร้อมวิธีสำรองข้อมูล |
| 0004 | รูปแบบเนื้อหาบทเรียน | JSON/YAML ที่ engine อ่าน / เขียนเป็นโค้ดต่อบท / แบบผสม |
| 0005 | สร้างอุปกรณ์จำลองอย่างไร | SVG / Canvas / DOM และ API กลางของ component |
| 0006 | อัลกอริทึมทบทวนเว้นระยะ | ช่วงเวลาคงที่ (Leitner) / SM-2 / แบบง่ายที่ Designer กำหนด |
| 0007 | กลยุทธ์การทดสอบ | unit test สำหรับ engine และตรวจเฉลย / ทดสอบบนเบราว์เซอร์สำหรับ interaction |

แต่ละข้อต้องเทียบข้อดีข้อเสียกับ N1–N9 และเลือกทางที่ง่ายที่สุดที่ตอบโจทย์

> **สถานะ (2026-09-29):** ตัดสินครบทั้ง 7 ข้อแล้ว ดูสรุปที่ [docs/architecture/overview.md](../docs/architecture/overview.md) ส่วน ADR-0006 ยังรอเกณฑ์จาก Learning Designer

## 6. หลักการออกแบบ

1. **แยก 3 ชั้นให้ชัด**
   - **เนื้อหา:** โจทย์ ข้อความ และเงื่อนไขจาก Lesson Spec
   - **Engine:** ลำดับช่วง การข้าม การตรวจคำตอบ การจับเวลาเงียบ และระบบทบทวน
   - **อุปกรณ์จำลอง:** component ภาพที่นำกลับมาใช้ได้
2. **อุปกรณ์จำลองเป็นชิ้นส่วนกลาง** ใช้ซ้ำได้ทุกวิชา มี API ชัดเจน (เช่น ค่า, โหมดแสดง/แฟลช/ซ่อน, event เมื่อลูกแตะ)
3. **ข้อมูลคำตอบเป็น event log** บันทึกทุกคำตอบเป็นรายการ แล้วคำนวณความก้าวหน้าจาก log เพื่อเปลี่ยนกติกาทบทวนภายหลังได้โดยไม่เสียข้อมูล
4. **เนื้อหาตรวจสอบได้อัตโนมัติ** ไฟล์เนื้อหามี schema และเทสต์ตรวจเฉลย
5. **เริ่มเล็ก** ทำบทเรียนแรกให้ใช้ได้จริงก่อน แล้วค่อยแยก engine เมื่อมีบทที่ 2–3 ให้เห็นรูปแบบซ้ำ

### 7.1 Architecture Overview — `docs/architecture/overview.md`
- ภาพรวมระบบ (แผนภาพ component)
- โครงสร้างโฟลเดอร์
- data model: ผู้เรียน, บทเรียน, ทักษะ, คำตอบ (event), ตารางทบทวน
- schema ของไฟล์เนื้อหาบทเรียน
- API ของอุปกรณ์จำลองแต่ละชิ้น

- มาตรฐานโค้ดและกลยุทธ์การทดสอบ
- วิธี build, run และ deploy

## 8. เช็คลิสต์ก่อนส่ง Tech Spec

- [ ] ทุกส่วนใน Lesson Spec มีที่อยู่ในระบบ หรือระบุชัดว่าไม่ทำเพราะอะไร (และ Designer รับทราบ)
- [ ] ไม่เปลี่ยนวิธีสอนเอง
- [ ] ใช้อุปกรณ์จำลองชุดเดิมให้มากที่สุด
- [ ] Acceptance Criteria ทดสอบได้จริงทุกข้อ
- [ ] มีเทสต์ตรวจเฉลยและเงื่อนไขโจทย์
- [ ] ไม่มีจุดที่แสดงเวลาให้ลูกเห็น
- [ ] ข้อมูลที่บันทึกพอสำหรับระบบทบทวนและหน้าสำหรับพ่อ
- [ ] สอดคล้องกับ ADR ทั้งหมด ถ้าต้องตัดสินใจใหม่ให้เขียน ADR ก่อน

## 9. การตรวจงานของ Developer

- ตรวจตาม Acceptance Criteria ทีละข้อ
- ตรวจว่าเป็นไปตาม ADR และมาตรฐานโค้ด
- ตรวจว่าเทสต์ครอบคลุมตามที่ระบุ และผ่านทั้งหมด
- ผ่านแล้วจึงส่งต่อให้ Learning Designer ตรวจด้านการสอน
