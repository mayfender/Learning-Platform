# ADR-0008: Event log: ลำดับ เวลา และการเพิ่ม field

- สถานะ: ยอมรับ
- วันที่: 2026-09-30
- เพิ่มเติมจาก: [ADR-0003](0003-local-storage-indexeddb.md)

## บริบท

ผล DX-ADD ครั้งแรกของลูกทำให้เจอ 2 เรื่องที่ ADR-0003 ยังไม่ได้กำหนด และ M2 (ADD-04) ต้องเพิ่ม event ใหม่จำนวนมาก (F9)

1. **ลำดับ event ผิด:** ในไฟล์ export `item.answered` ของข้อสุดท้าย (5.4) อยู่หลัง `session.completed` ทั้งที่ `at` เท่ากันที่ระดับมิลลิวินาที สาเหตุอยู่ที่การเรียงตอนอ่าน (`at` แล้วตามด้วย `id` ซึ่งเป็น UUID สุ่ม) ไม่ใช่ที่ลำดับการเขียน (รายละเอียดใน [Tech Spec DX-ADD §14.2](../specs/DX-ADD-diagnostic.md))
2. **`at` ไม่ใช่เวลาตอบ:** `at` ถูกประทับตอน emit ข้อที่ถามวิธีคิดจะ emit หลังเลือกวิธีคิด `at` จึงเป็นเวลาเลือกวิธีคิดเสร็จ (ช้ากว่าเวลาตอบประมาณ 1 วินาทีของข้อความ ack บวกเวลาเลือก)
3. **ยังไม่มีกติกาเพิ่ม field:** ADR-0003 ข้อ 7 ให้ bump `schemaVersion` เมื่อเปลี่ยนโครงสร้าง แต่ไม่ได้แยกว่าการเพิ่ม field เสริมต้อง bump หรือไม่ ถ้า bump ทุกครั้งจะต้องเขียน migration ที่ไม่ทำอะไรเลยไปเรื่อยๆ

## ทางเลือก

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| เก็บเลขลำดับ `seq` ต่อ session | เรียงได้แน่นอน | ต้องแก้ทุกที่ที่สร้าง event, event เก่าไม่มี, ต้อง merge กับ `at` ตอนรวมหลาย session |
| ปรับให้ `at` เพิ่มขึ้นเคร่งครัดในทุก session (monotonic) และใช้ตัวเรียงกลางที่เรียงตามชนิดเมื่อ `at` เท่ากัน | แก้ที่เดียว ใช้กับ event เก่าที่ `at` ซ้ำอยู่แล้วได้โดยไม่แก้ข้อมูล | เวลาอาจล้ำหน้านาฬิกาจริงไม่กี่ ms |
| bump `schemaVersion` ทุกครั้งที่เพิ่ม field | ชัดเจน | ต้องมี migration ว่างและเทสต์ทุกครั้ง โดยไม่จำเป็น |

## การตัดสินใจ

1. **`at` = เวลาที่ event ถูกบันทึก** (ประทับตอน emit) ไม่ใช่เวลาที่เหตุการณ์เกิดจริง เวลาเหตุการณ์ที่ต่างจากเวลาบันทึกต้องเป็น field แยก (เช่น `answeredAt` ของ `item.answered`) และเอกสารของ event ต้องระบุความหมายของ field เวลาทุกตัว
2. **`at` เพิ่มขึ้นเคร่งครัดภายใน session เดียว:** ตัวสร้าง event (runner) เก็บ `lastAtMs` ของ session แล้วประทับ `max(Date.now(), lastAtMs + 1)` เป็น ISO string (รูปแบบ `toISOString()` เสมอ) event ในชุดเดียวกัน (transition เดียว) จึงมี `at` ต่างกันตามลำดับที่ emit
3. **ตัวเรียงกลาง `compareEvents`** (`src/store/eventOrder.ts`) เรียงตาม `at` แล้วตามลำดับชนิด แล้วตาม `id` ทุกที่ที่เรียง event ต้องใช้ตัวนี้ตัวเดียว (`MemoryStore`, `IndexedDbStore`, export) ส่วน `groupSessions` (engine) import จาก store ไม่ได้ตามกฎ ESLint จึงเรียงตาม `at` แบบเสถียรบนลำดับที่ store เรียงไว้แล้ว (ตัดสิน 2026-09-30)
   ลำดับชนิด: `session.started` 0 · `block.started` 1 · `item.answered` และ `strategy.reported` 2 · `block.completed` และ `parent.noted` 3 · `session.completed` และ `session.abandoned` 4
   ข้อนี้ทำให้ event เก่าที่ `at` เท่ากัน (เช่น session ของ DX-ADD ที่บันทึกไปแล้ว) อ่านออกมาถูกลำดับโดยไม่ต้องแก้ข้อมูลใน log (log ยังเพิ่มอย่างเดียว)
4. **การเพิ่ม field เสริม (optional) หรือชนิด event ใหม่ ไม่ต้อง bump `schemaVersion`** ตัวอ่านต้องรับ `undefined` ของ field ที่เพิ่มมาทีหลังเสมอ และ `isAppEvent` ตรวจ field ใหม่เฉพาะเมื่อมีค่า
   **ต้อง bump** (พร้อม migration ใน `store/migrations.ts` และเทสต์) เมื่อ: เปลี่ยนความหมายของ field เดิม, เปลี่ยนชนิดข้อมูลของ field เดิม, ลบ field, หรือทำให้ field เดิมกลายเป็นบังคับ
5. **ห้ามเขียนทับหรือลบ event ใน log** ถ้าต้องแก้ข้อมูลที่บันทึกผิด ให้เพิ่ม event ชนิดใหม่ที่ชี้ถึงของเดิม (เช่น `parent.noted` ครั้งใหม่แทนครั้งก่อน อ่านโดยถือครั้งล่าสุดเป็นค่าปัจจุบัน)
6. **event เก่าที่ไม่มี field ใหม่:** ผู้อ่านต้องมีทางสำรองที่ระบุไว้ เช่น เวลาตอบของ event เก่า = `at` (ประมาณ ± เวลาเลือกวิธีคิด) ดู helper `answerTime()` ใน Tech Spec DX-ADD §14.3

## ผลที่ตามมา

- แก้บั๊กลำดับ event ที่เดียว และข้อมูลเก่าอ่านถูกโดยไม่ต้องแตะ log
- ทุก Tech Spec ต่อไปกำหนดชนิด/field ใหม่ได้โดยไม่ต้องทำ migration ถ้าเป็นแค่การเพิ่ม
- ความเสี่ยงที่ต้องรู้: ถ้าเครื่องใช้แอปรุ่นเก่ากว่า (เช่น PWA ที่ยังไม่อัปเดต) อ่านข้อมูลที่รุ่นใหม่เขียนไว้ `listEvents` จะ throw เมื่อเจอชนิด event ที่ไม่รู้จัก ปัจจุบันแอปอัปเดตตัวเองผ่านแบนเนอร์ และไม่รองรับการย้อนรุ่น (ไม่ทำอะไรเพิ่ม ถ้าพบว่าเป็นปัญหาจริงให้เปิด ADR ใหม่เรื่องการอ่านแบบทนต่อ event ที่ไม่รู้จัก)
- ต้องมีเทสต์ contract ของ store: เขียน event ที่ `at` เท่ากันโดย `id` เรียงสวนกับลำดับที่ถูก แล้วอ่านต้องได้ลำดับที่ถูก
