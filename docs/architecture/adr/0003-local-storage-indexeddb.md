# ADR-0003: เก็บความก้าวหน้าใน IndexedDB แบบ event log พร้อม export/import

- สถานะ: ยอมรับ
- วันที่: 2026-09-29

## บริบท
เจ้าของโปรเจกต์เลือกเก็บข้อมูลในเครื่อง (ADR-0001) ข้อมูลต้องไม่หายเมื่อ deploy เวอร์ชันใหม่ (N7) ต้องพอใช้กับระบบทบทวนและหน้าสำหรับพ่อ (F8–F10) และต้องส่งให้ AI วิเคราะห์ได้

ความเสี่ยงที่พบ:
- ผู้ใช้หรือเบราว์เซอร์อาจล้างข้อมูลเว็บ
- **Safari (iPad/iPhone) ลบข้อมูลของเว็บที่ไม่ได้เปิดใช้ 7 วัน** ยกเว้นเว็บที่ติดตั้งบนหน้าจอ (PWA)

## ทางเลือก
| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| localStorage | ง่าย | จุได้น้อย เป็น sync API และถูกลบง่าย |
| **IndexedDB** | จุได้มาก เป็น async API และขอสิทธิ์ persistent ได้ | API ซับซ้อน (แก้ด้วย library `idb`) |
| Cloud DB | ข้อมูลไม่หาย | ขัดกับทางเลือกของเจ้าของโปรเจกต์ |

## การตัดสินใจ
1. เก็บใน **IndexedDB ผ่าน library `idb`**
2. เก็บข้อมูลเป็น **event log ที่เพิ่มอย่างเดียว ไม่แก้ไข** ความก้าวหน้าและตารางทบทวนคำนวณจาก log ทุกครั้ง (อาจ cache ได้แต่ log คือความจริง)
3. ทุกส่วนของแอปเข้าถึงข้อมูลผ่าน interface `ProgressStore` เท่านั้น
   - `IndexedDbStore` ใช้งานจริง
   - `MemoryStore` ใช้ในเทสต์
   - ถ้าวันหน้าต้องการ sync ให้เพิ่ม adapter ใหม่ (เช่น Supabase) โดยไม่แก้ส่วนอื่น
4. เรียก `navigator.storage.persist()` ตอนเปิดแอปครั้งแรก
5. **Export/Import เป็นไฟล์ JSON** จากหน้าสำหรับพ่อ ใช้สำรองข้อมูล ย้ายเครื่อง และส่งให้ AI (Learning Designer) วิเคราะห์
6. เตือนในหน้าสำหรับพ่อถ้าไม่ได้ export เกิน 7 วัน และแนะนำให้ติดตั้งเป็น PWA บน iPad/iPhone
7. ข้อมูลทุกชุดมี `schemaVersion` ถ้าเปลี่ยนโครงสร้าง ต้องมี migration ใน `store/migrations.ts` พร้อมเทสต์
8. ไม่เก็บชื่อจริง ใช้ชื่อเล่นที่ตั้งเองในแอป

## ผลที่ตามมา
- ข้อมูลอยู่แค่ในเครื่องเดียว ถ้าลูกใช้หลายเครื่อง ผลจะแยกกัน (ใช้ import รวมได้ เพราะ event มี id ไม่ซ้ำ จึงรวมโดยตัดตัวซ้ำได้)
- ต้องทำหน้า export/import ตั้งแต่เวอร์ชันแรก เพราะเป็นทางเดียวที่ AI จะได้เห็นผล
