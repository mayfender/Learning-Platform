# ADR-0007: กลยุทธ์การทดสอบ — Vitest + Playwright

- สถานะ: ยอมรับ
- วันที่: 2026-09-29

## บริบท
เนื้อหาต้องถูกต้อง 100% (N5) ต้องใช้ได้บน Android, มือถือ, คอมพิวเตอร์ และ iPad (N1) และ AI เป็นคนเขียนโค้ด จึงต้องมีเทสต์เป็นตาข่ายกันพลาด

## การตัดสินใจ

### ชั้นที่ 1: Unit test (Vitest)
- **เทสต์ตรวจเนื้อหาอัตโนมัติ** (`src/content/content.test.ts`) วนทุกบทเรียนและแบบทดสอบที่ลงทะเบียนไว้
  - คำนวณเฉลยจากโจทย์แล้วเทียบกับเฉลยที่ระบุ
  - ตัวเลือกไม่ซ้ำกัน มีเฉลยอยู่ในตัวเลือก และตัวเลือกผิดทุกตัวผูกกับรหัสความเข้าใจผิดที่มีอยู่จริง
  - generator: สุ่มอย่างน้อย 500 ครั้งด้วย seed ต่างกัน แล้วตรวจเงื่อนไข (เช่น ข้ามสิบทุกข้อ)
  - ทักษะที่อ้างถึงมีอยู่ใน `skills.ts`
- engine: reducer ของบทเรียน เงื่อนไขข้าม การตรวจคำตอบ การคำนวณผลวินิจฉัย และ Leitner
- store: `MemoryStore` กับ `IndexedDbStore` ผ่านชุดเทสต์เดียวกัน (ใช้ `fake-indexeddb`), migration และ export/import

### ชั้นที่ 2: Component test (Vitest + Testing Library)
- อุปกรณ์จำลอง: แสดงค่าถูก โหมด flash ซ่อนตามเวลา (ใช้ fake timers) และตอบสนองการแตะ

### ชั้นที่ 3: End-to-end (Playwright)
ทดสอบบน 3 project (ทุกตัวเป็น Chromium)
| Project | จำลอง |
|---|---|
| `android-tablet` | Chromium ขนาดแท็บเล็ต Android แบบแตะ |
| `phone` | Chromium ขนาด Pixel (≈ 412px) แบบแตะ |
| `desktop` | Chromium จอคอมพิวเตอร์ |

ทุก flow หลักต้องมี e2e: ทำจนจบ ตรวจว่าไม่มีตัวจับเวลาแสดง ไม่มี scroll แนวนอน dark mode และข้อมูลยังอยู่หลัง reload

### เกณฑ์
- `npm test` (unit + component) และ `npm run e2e` ต้องผ่านก่อนส่งงานทุกครั้ง
- CI (GitHub Actions) รันทั้งสองชุดก่อน deploy ถ้าไม่ผ่านห้าม deploy

## ผลที่ตามมา
- ก่อนปล่อยฟีเจอร์ใหญ่ ให้ลองบนแท็บเล็ตจริงของลูกอย่างน้อย 1 ครั้ง
- ระหว่างพัฒนาให้รันเฉพาะ project ที่เกี่ยวข้อง (เช่น `--project=android-tablet`) แล้วรันครบทุก project ครั้งเดียวตอนส่งงาน และใน CI

## แก้ไข 2026-09-30: ตัด iPad (WebKit) ออก
พ่อตัดสินว่าลูกไม่ได้ใช้ iPad จึงตัด project `ipad` ออกเพื่อลดเวลาทดสอบ iPad/Safari ยังเปิดใช้ได้แบบ best-effort แต่ไม่รับประกันและไม่ถือเป็นเงื่อนไขปล่อยงาน ถ้าวันหน้าต้องรองรับ ให้เพิ่ม project กลับมาได้ที่ `playwright.config.ts`
